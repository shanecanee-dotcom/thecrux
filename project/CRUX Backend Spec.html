01

Where we are & where we're going

Overview

CRUX today is a local-first React app with no server. Everything a climber logs lives in their browser's localStorage under a handful of keys. There are no accounts — the app implicitly belongs to whoever is holding the phone. Clear the browser, lose your data; switch devices, start over.

To put it live for real users we need three things the prototype lacks: identity (who is this?), durable storage (data that survives a device), and isolation (my logbook is mine, not yours). This document specifies all three, plus the photo handling, sync behaviour, and data-protection obligations that come with them.

Guiding principles

PrincipleWhat it means here
Stay local-firstThe app already writes locally and feels instant. The backend mirrors that store — it doesn't replace it. Climbers log sends in gyms with bad signal; the app must never block on the network.
One small leapPick a managed platform so one person can ship and run this. No fleet of microservices for a logbook app.
Model for tomorrowShip isolated accounts now, but shape the schema so per-gym leaderboards and following don't need a rewrite.
Own the dataUK-based product → UK/EU data residency, full export, and real deletion from day one.

What "multiple users" means in v1

Each person gets a private account and their own logbook. No social features are exposed yet — but gyms become a shared, canonical entity (rather than free text), which is the single schema decision that unlocks leaderboards and gym feeds later without a migration.

Default decisionIsolated multi-user now; social-ready schema. If you want following / leaderboards in v1, say so — it changes scope in §08 but not the foundations.

Scope of this document

  • In scope: stack choice, auth, the relational data model, row-level security, the client↔server sync strategy, photo/object storage, migrating existing local data, GDPR posture, and a phased rollout.
  • Out of scope (noted where relevant): native app packaging, push notifications, payments, and the social graph itself — all called out as future phases.

Architecture & stack

System shape

The whole thing is a thin sync layer between the existing app and a managed Postgres. No bespoke server to babysit.

CRUX client (React)
Existing UI, unchanged behaviour. Reads/writes a local cache first; queues changes for sync.
Local cache
IndexedDB (replaces today's localStorage). Source of truth for instant reads & offline writes.
Supabase — managed backend
Auth · Postgres (with Row-Level Security) · Storage (photos) · auto-generated REST & Realtime APIs. Hosted in EU/UK region.
Auth
Email + password, magic link, Google, Apple. Issues JWTs.
Postgres + RLS
Per-row ownership enforced in the database itself.
Object storage
Climb photos & avatars + thumbnails.

Why Supabase (the default)

It bundles exactly the four pieces this app needs — auth, a real relational database, file storage, and an auto-generated API — behind one managed service, and it's plain Postgres underneath so we're never locked into a proprietary query model.

NeedSupabase gives usAlternative considered
Accounts & sign-inHosted Auth with email/password, magic link, Google & Apple OAuth, JWT issuanceAuth0, Clerk (more $$ at scale)
Durable dataManaged Postgres — relational, exactly fits sessions→climbsFirebase/Firestore (document model fights our relations)
IsolationRow-Level Security in the DB — the rule travels with the dataHand-rolled checks in an API layer (easy to get wrong)

Migration safety valve: because it's standard Postgres, if we ever outgrow the platform we lift the database and storage out and front it with our own API. The data model in §04 stays identical either way.
DecideRegion must be set at project creation and can't be moved later. Default: eu-west-2 (London) for UK residency.

Hosting the client

The CRUX front-end is static (HTML/JS) — deploy it to any static host or CDN (Vercel, Netlify, Cloudflare Pages). It talks to Supabase directly via the SDK using a public "anon" key; all real authority lives in the RLS policies, not the client.

03

Identity & authentication

Who is this?

Auth is handled by Supabase Auth. A successful sign-in yields a JWT carrying the user's id (a UUID). Every database request rides that token, and Postgres reads the id as auth.uid() inside RLS policies — so identity and authorisation are the same fact.

Sign-in methods (v1)

MethodNotes
Email + passwordBaseline. Includes verification email & password reset out of the box.
Magic linkPasswordless — tap a link in email. Lowest friction for a casual logging app.
GoogleOAuth. One-tap on Android & web.
AppleOAuth. Required by Apple if we ever wrap this as an iOS app and offer any other social login.

The onboarding the app already has

CRUX has an onboarding flow (crux_onboarded, name + home-gym capture). That stays — it simply runs after first sign-in and writes to the profiles row instead of localStorage. Returning users skip straight in.

Anonymous → account (smooth migration)

Existing users already have a local logbook and no account. On first launch of the live version:

  1. Detect local data in localStorage / IndexedDB.
  2. Offer "Create an account to back this up" — or continue anonymously (Supabase supports anonymous sessions that can be upgraded later).
  3. On account creation, the local data is pushed up under the new user_id (see §09 Migration).
Default decisionAllow anonymous sessions so the app works the instant it loads, then nudge to register. This preserves the current "just start logging" feel.

05

Schema

SQL DDL

Postgres definitions. Enums mirror the constants in crux-data.jsx (WALL_TYPES, HOLD_COLORS, outcomes, grade systems). Every owned row carries user_id, updated_at and a soft-delete flag for sync.

-- enums mirror the app's constants
create type grade_system as enum ('v', 'font');
create type climb_outcome as enum ('attempt', 'sent', 'flash');
create type wall_type as enum ('slab', 'vert', 'overhang', 'cave');

-- canonical gyms (shared across users)
create table gyms (
  id          uuid primary key default gen_random_uuid(),
  name        text not null,
  city        text,
  country     text,
  created_by  uuid references auth.users,
  created_at  timestamptz not null default now()
);

-- one row per user; extends Supabase's auth.users
create table profiles (
  id           uuid primary key references auth.users on delete cascade,
  display_name text,
  home_gym_id  uuid references gyms,
  avatar_path  text,                  -- key in storage, not base64
  goals        jsonb not null default '{"weeklySessions":3}',
  settings     jsonb not null default '{}',  -- theme, rest, gradePref…
  onboarded_at timestamptz,
  updated_at   timestamptz not null default now()
);

create table sessions (
  id          uuid primary key default gen_random_uuid(),
  user_id     uuid not null references auth.users on delete cascade,
  gym_id      uuid references gyms,
  gym_name    text,                   -- free-text fallback / snapshot
  started_at  timestamptz not null,
  ended_at    timestamptz,            -- null = session in progress
  deleted_at  timestamptz,            -- soft delete for sync
  updated_at  timestamptz not null default now()
);

create table climbs (
  id           uuid primary key default gen_random_uuid(),
  session_id   uuid not null references sessions on delete cascade,
  user_id      uuid not null references auth.users on delete cascade,
  grade_system grade_system,
  grade        text,                  -- e.g. 'V5' or '6C+'
  outcome      climb_outcome not null default 'attempt',
  attempts     int not null default 1,
  wall         wall_type,
  hold_color   text,                  -- 'red'…'grey' (see HOLD_COLORS)
  photo_path   text,                  -- key in storage
  note         text,
  logged_at    timestamptz not null,
  deleted_at   timestamptz,
  updated_at   timestamptz not null default now()
);

-- indexes for the queries the app actually runs
create index on sessions (user_id, started_at desc);
create index on climbs   (user_id, logged_at desc);
create index on climbs   (session_id);
IDs change shape: the app's uid() makes short 7-char strings, fine for a local array but not globally unique. New rows use server-side UUIDs; on migration we map old ids → new UUIDs (§09).

06

Row-Level Security

Isolation

This is the heart of "multiple users." Rather than trust the client or an API layer to filter by user, we make the database itself refuse to return or modify rows that aren't yours. The policy is attached to the table; there is no code path around it.

-- lock every owned table down by default
alter table profiles enable row level security;
alter table sessions enable row level security;
alter table climbs   enable row level security;

-- a user sees and writes only their own rows
create policy "own sessions" on sessions
  for all
  using      (user_id = auth.uid())   -- read/update/delete
  with check (user_id = auth.uid());  -- insert/update

create policy "own climbs" on climbs
  for all
  using      (user_id = auth.uid())
  with check (user_id = auth.uid());

create policy "own profile" on profiles
  for all using (id = auth.uid()) with check (id = auth.uid());

-- gyms are shared: anyone signed in can read; anyone can add one
alter table gyms enable row level security;
create policy "read gyms"   on gyms for select using (true);
create policy "create gyms" on gyms for insert with check (auth.uid() is not null);
Why this mattersWith RLS on, a bug in the client or a leaked anon key still can't read someone else's logbook — the worst case is a user over-fetching their own data. Authorisation can't be forgotten because it isn't in application code.

When social arrives

Leaderboards and feeds become additive policies, e.g. "members of gym X may read each other's sent climbs at that gym." We add policies; we never loosen the owner-only default. A visibility column (private / gym / public) on sessions gives users control before any of that ships.

API & access patterns

How the app talks

No custom API is written for v1 — the Supabase client SDK exposes the tables directly (guarded by RLS). Below are the real operations the current UI performs, mapped to calls.

App action (today)Operation
Start a sessioninsert sessions (gym, started_at)
Log a climbinsert climbs (session_id, grade, outcome, …)
Mark sent / flash, change attemptsupdate climbs set outcome, attempts
End sessionupdate sessions set ended_at
History listselect sessions order by started_at desc
Stats / achievementsselect climbs → computeDerived() client-side
Edit profile / goals / settingsupdate profiles
Add a photostorage.upload() → store path on climb

Reads stay cheap

The home and stats screens need the user's whole (modest) climb history to compute streaks and bests. That's a single indexed query per user — trivial at the hundreds-to-thousands-of-rows scale a personal logbook generates. No aggregation service required.

Where a server function would earn its place

  • Leaderboards across many users — a scheduled job or Postgres view that ranks max(grade) per gym per week, so clients don't fetch others' raw data.
  • Account deletion — a function that purges rows and storage objects in one transaction (§10).
  • Abuse / rate limits on gym creation, once gyms are public.

All three are Phase 2+. None are needed to go live.

08

Local-first sync

Offline behaviour

Climbers log mid-session in basements with no signal. The app must keep working and reconcile later. We preserve the current "write locally, instantly" feel and layer sync underneath.

Read path

UI reads from the local cache (IndexedDB) — always instant, online or off. A background pull refreshes the cache from Postgres on launch and on reconnect.

Write path

Every change writes to the local cache immediately and enqueues an outbound mutation. The queue drains to Supabase when there's a connection.

Conflict resolution

A personal logbook on one-or-two devices rarely produces true conflicts. We use last-write-wins per row via the updated_at column: the newer timestamp wins. Deletes are soft (deleted_at) so a delete on one device propagates instead of being resurrected by a stale copy on another.

Because climbs are individual rows (not one big JSON blob), two devices editing different climbs in the same session never collide — they merge cleanly. This is a direct payoff of the relational split in §04.

Implementation options

OptionEffortWhen
Hand-rolled queue + updated_at reconciliationLow–medDefault for v1 — full control, few moving parts
Realtime subscriptions (Supabase)LowAdd when multi-device live updates matter
Off-the-shelf sync engineMedOnly if the logbook grows collaborative
Default decisionShip the simple queue. It covers the real use case (one climber, occasionally two devices) without taking on a sync framework.

Photos & data migration

Blobs & backfill

Photos: out of the database

Today a climb photo and the avatar are stored as base64 data URLs inside the JSON. That's fine for a prototype and ruinous at scale — a few photos bloat every read and blow past row/storage limits. They move to object storage:

  • Upload the file to a Storage bucket at e.g. climbs/{user_id}/{climb_id}.jpg.
  • Store only the path on the row (photo_path, avatar_path).
  • Bucket is private; the client fetches via short-lived signed URLs. Generate a thumbnail on upload for list views.
DecideCompress/resize on the client before upload (e.g. longest edge 1600px, JPEG ~0.8). Keeps storage and bandwidth sane on mobile data.

Migrating existing local data

The app already has an export feature (exportData() bundles sessions, profile, goals, tweaks to JSON) — that same shape is exactly what we import. On first authenticated launch:

  1. Read local crux_* keys (or an imported export file).
  2. For each session & climb, generate a new UUID and remember the old→new id map.
  3. Insert sessions then climbs under the new user_id; map grade.system/grade, wallType→wall, holdColor→hold_color, time→logged_at.
  4. For any embedded base64 photo, upload to storage and set photo_path.
  5. Write profile/goals/tweaks into the profiles row; set onboarded_at.
  6. Mark local data "migrated" so it isn't re-imported; keep it as a local backup until the first successful pull confirms.
No user loses anything. The migration is idempotent and runs once per device; the original local copy is retained until cloud sync is verified.

Data protection

UK GDPR

A UK product holding personal data (email, name, photos, location-ish gym data) sits under UK GDPR. None of this is heavy for a logbook, but it must be designed in, not bolted on.

ObligationHow we meet it
Data residencyEU/UK region (eu-west-2). Set at project creation.
Right to access / portabilityReuse exportData() — already produces a full JSON export. Expose it as "Download my data."
Right to erasure"Delete account" → a server function that deletes the auth.users row (cascades to all tables) and purges the user's storage folder. Real deletion, not a flag.
Data minimisationWe store only what's logged. No tracking, no third-party analytics by default.
SecurityEncryption in transit & at rest (managed), RLS isolation, private photo bucket with signed URLs.
Consent & transparencyShort privacy notice at sign-up; explicit opt-in before any future social/leaderboard visibility.
Before launchA lightweight privacy policy and terms page. Confirm Supabase's DPA/sub-processor terms are acceptable (they offer a standard DPA).
